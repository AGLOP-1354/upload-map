# 작업 원칙

출처: Karpathy 코딩 가이드라인(andrej-karpathy-skills) + obra/superpowers의 verification / systematic-debugging을 이 프로젝트 규모에 맞게 압축.

## 1. 코딩 전에 생각한다
- 가정을 먼저 밝힌다. 요구가 두 가지로 해석되면 고르지 말고 묻는다.
- 더 단순한 방법이 있으면 말한다. 필요하면 반대 의견을 낸다.

## 2. 단순함이 먼저
- 요청받은 것만 만든다. 추측성 기능·설정 옵션·추상화 금지.
- 1인용 로컬 앱이다: 인증, 멀티유저, 동시성 제어, 국제화, 외부 DB는 요청 없으면 만들지 않는다.
- 200줄로 쓴 걸 50줄로 쓸 수 있으면 다시 쓴다.

## 3. 외과적 수정
- 바뀐 모든 줄은 요청으로 거슬러 올라갈 수 있어야 한다.
- 옆 코드의 스타일 정리·리팩터링·주석 수정은 하지 않는다. 눈에 띄면 말만 한다.
- 내 변경으로 안 쓰이게 된 import/변수/함수만 지운다.

## 4. 목표 기반 실행
- 작업을 "검증 가능한 목표"로 바꾼다. 예: "버그 수정" → "재현 → 수정 → 재현 안 됨 확인".
- 여러 단계면 단계마다 `무엇을 → 어떻게 확인` 을 적는다.

## 5. 증거 없이 완료라고 말하지 않는다
완료·수정됨·통과 같은 말을 하기 전에:
1. 그 주장을 증명하는 명령이 뭔지 정한다 (`npm run lint`, `npx tsc --noEmit`, 화면 확인 등).
2. 지금 실행한다. 이전 실행 결과나 "아마 될 것"은 증거가 아니다.
3. 출력을 끝까지 읽는다.
4. 결과대로 보고한다. 실패했으면 실패했다고, 확인 못 한 건 못 했다고 쓴다.
UI 변경은 `/verify`로 실제 페이지까지 확인한다.

## 6. 원인 없이 고치지 않는다
버그가 나면 바로 패치하지 말고: 재현 → 에러/스택을 끝까지 읽기 → 최근 변경 확인 → 가설 하나 세우고 최소 변경으로 검증 → 원인 확정 후 수정.
같은 문제에 수정 시도가 3번 실패하면 멈추고 접근을 다시 검토한다 (자세한 절차: `/debug`).
